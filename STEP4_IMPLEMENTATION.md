# BookAI — Step 4: Customer/supplier balances, payment allocations and bank reconciliation

## Scope and UI preservation

This source-only package includes **Steps 1–4**. It retains `src/styles.css` byte-for-byte, the sidebar, fonts, four workflow choices, existing AI chat/drop-zone, Review Queue, company picker and navigation. New controls are added as sections inside **Accounts**, **Bank Reconciliation** and **Reports → Management Analysis**. No new main tabs, CSS redesign, external bank integration, payment execution or automated GL posting were added.

## What was implemented

1. **Operational customer/supplier schedules:** `partyBalances` combines only approved invoices, credits, receipts, payments and dated allocations as of a selected date/currency; it groups by counterparty and separates overdue aging (current, 1–30, 31–60, 61+ days), open invoice amounts, unallocated cash and net control amounts. An exported CSV lists actual open invoices.
2. **Bookkeeper-confirmed settlement allocation:** **Accounts → Open balances & payment allocation** offers only approved, same-party, same-currency and compatible customer/supplier invoice/payment pairs. User selects actual amount, allocation date and an audit evidence/reference note. The existing engine prevents over-allocations, wrong parties, duplicate action retries, closed periods and impossible historical allocations. Allocations update operational open balances but **never invent a new bank transaction or general journal**.
3. **Audited GL control account mapping:** The human reviewer selects actual active approved **Asset** codes for customer receivables and individual bank accounts, and a **Liability** code for suppliers. Validation rejects unknown, inactive, wrong-type and duplicate control mappings; later approved-chart changes cannot invalidate existing saved mappings. Company mappings persist in the original company workspace state via the existing authenticated action API. No GL code is guessed by AI.
4. **A/R and A/P GL control checks:** **Reports → Management Analysis** displays operational net vs internal posted GL balance and exact minor-unit differences for selected company/currency/date. It checks that the opening journal is present and all relevant approved source documents have posted journals; otherwise it reports **Unmapped** or **Incomplete**, never **Balanced** merely because both sides happen to be zero. A/P is shown as a credit-normal liability.
5. **Bank statement control totals:** The existing validated `bank-import` action now retains each import's account, currency, opening/closing balance, derived last row date, row count and statement ID. The record is added atomically only if signed rows roll forward exactly to the declared closing balance. Individual imported rows keep an immutable statement-batch link. Previously imported legacy rows remain readable, though older closing balances cannot be reconstructed from rows alone.
6. **Manual / exact cash matches:** Inside **Bank Reconciliation**, reviewers can inspect imported statement rows, choose eligible approved cash movements, and confirm each one once only. Exact reference/date/amount suggestions come from the existing conservative matching rule; a non-exact match additionally requires a written discrepancy explanation. Wrong bank, currency, sign, amount, invoice-only source, double use and closed-period matches are blocked. This records an internal bank/source **match**, not a GL journal or actual bank action.
7. **Cashbook and bank-to-GL report:** The bank panel displays a dated cashbook, CSV export, matched/unmatched status and whether each cash document has a posted internal journal. Each saved statement compares its closing balance against the reviewer-mapped GL bank balance as of its last transaction date, displaying differences. It marks reconciliation **Incomplete** if the GL mapping/opening balance is missing, bank rows are unmatched, cashbook movements remain unmatched, or matched documents lack journals; it marks **Difference** when otherwise complete but balances disagree.
8. **Currency and legacy compatibility:** Calculations stay in integer minor units, currencies are not combined, and older company JSON states without `bankStatements` or `controlAccounts` load with missing-control/incomplete indicators. The Management Analysis headline KPIs now honor the selected client currency.

## How to use

1. **Client Configuration:** Save your genuine client chart in the original `Code | Name | Type | Active` Markdown table format; import and verify the opening trial balance (Step 2). Verify the company, currency and account names before proceeding.
2. **AI workspace + Review Queue:** Upload genuine invoices, receipts, and statements. Review document and journal proposals with original evidence (Step 3). Approve the proposed journals as appropriate. The AI is not an autonomous bookkeeper.
3. **Accounts:** Scroll below the existing records table to **Open balances & payment allocation**. Choose **Customers (AR)** or **Suppliers (AP)** and an as-of date. Check open amounts, aging, unallocated payments and the invoice export. Choose a compatible invoice/payment pair, enter the exact allocated amount/date and a payment-advice/reviewer reference, then **Confirm allocation**. Audit history records the details.
4. **Bank Reconciliation workflow:** Select the bank and as-of date. Select the correct **GL asset control code** for that bank and save it. Imported statement batches show closing balances and GL differences. For each unmatched statement row, inspect source evidence, choose the approved cash document, enter a reviewer note (mandatory for non-exact matching), then **Confirm reviewed cash match**. Inspect cashbook, missing journal warnings and unmatched rows.
5. **Reports → Management Analysis:** Review the **Receivables and payables vs ledger** section. Pick the proper approved GL Asset/Liability codes once for the current client. The status is **Balanced** only with opening journal, complete internal journal coverage and equal control totals. Investigate any difference; do not override statuses manually.
6. **Audit log:** Review each `allocate`, `bank-match`, `bank-import`, `control-map` and `journal` action. Every operation is company-scoped and uses the same action/revision safeguards as the existing application.

## Limits and next step

- This is a **basic, reviewer-controlled** reconciliation. It does not import a bank feed directly from the bank or automatically create journal adjusting entries, calculate unrecorded interest/fees, support multiple split bank-to-one-cash matches, record deposits in transit as signed reconciling items, or prove external source completeness. Keep unexplained differences unresolved until properly evidenced and journaled.
- Past statement imports from Steps 1–3 do not contain recorded batch closing balances. The app does not invent missing historical statements or bank balances.
- An operational settlement allocation is not an additional GL posting: properly supported and approved invoice, receipt/payment and any adjustment journals must exist separately.
- No VAT/SST statutory filing, bank transfer, tax filing, e-invoice submission or external accounting platform sync takes place.
- **Next Step 5:** independently verify complete ledger classifications and begin reliable financial statements (P&L, balance sheet) and reports with completeness warnings; reserve monthly closing controls for Step 6.

## Safe install / deploy

1. Back up existing Git repository, actual `.env` credentials separately, and production Supabase data. Do **not** replace your `.env` or delete `.git`.
2. Extract the **contents** of `BookAI_Step4_Keep_Original_UI.zip` into your project repository root (not a new nested directory). It includes all Step 1–4 changes; no need to apply earlier ZIPs separately.
3. Use your project's supported Node version, install normal dependencies, and run `npm ci`, `npm test`, `npm run build`, `npm run check:server`.
4. In a test company, exercise approved source → GL journal → partial allocation → statement import → exact/manual match → GL mapping → report reconciliation → audit. Include wrong-currency, duplicate, unmatched, and incomplete-ledger scenarios.
5. Visually compare original and updated screens on mobile and desktop; check date/amount entry and scrolling. Deploy only after verification with your existing deployment pipeline. `/version.json` included in this archive reports `source_only_not_deployed` and must not be read as proof of deployment.
